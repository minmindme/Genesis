## 一、缘起：一个哲学问题

一切始于一个 PowerDesigner 建模问题，和一句话：**"一生二，二生三，三生万物。"**

传统架构里，每新增一个业务就长出一张表——万物各自成形，从未归一。这个项目的追问是：能否反过来，**让万物先归于"一"（一张同构表），再由规则分化出"万物"（任何业务形态）？**

推演收敛为四条公理：

1. **万物皆数**：数据库里只有一张 `UniversalEntity` 表。业务数据、元数据、引擎指令，全部是这张表里结构相同的行。
2. **数据库只负责存**：不 JOIN、不视图、不计算。它是哑巴硬盘，不是思考者。
3. **引擎同化**：引擎的规则（表长什么样、路由到哪）本身也是行（Role=4），C# 代码里没有业务逻辑，引擎退化为"寻址器"。
4. **零计算**：无 JOIN、无序列化、无反射式 ORM 映射，只有指针巡航。

本白皮书回答一个诚实的工程问题：**这套哲学在物理世界里到底能跑多快，代价是什么。**

## 二、架构总览

### 2.1 唯一的一：UniversalEntity 表（9 列）

| 列 | 类型 | 语义 |
|---|---|---|
| Id | UNIQUEIDENTIFIER | 行标识（Guid 占位，防遍历） |
| TypeId | UNIQUEIDENTIFIER | 类型指针：指向定义"我是谁"的元数据行 |
| Role | TINYINT | 角色同化：1=Meta / 2=Data / 3=Edge / 4=Engine |
| ParentId | UNIQUEIDENTIFIER? | 图指针：树/边/归属，一行既是数据也是路由 |
| Value | NVARCHAR(MAX) | 纯值，无 JSON 结构 |
| Version / IsDeleted / CreatedAt / UpdatedAt | | 系统控制 |

**没有外键、没有第二张表、没有任何业务语义列。**

### 2.2 引擎组件（Emoking.DAL）

| 组件 | 职责 | 关键事实 |
|---|---|---|
| `MetaCache` | 自举加载 Role=1/4 → 内存字典；**池空时自动幂等播种创世行** | 引擎的灵魂只存在于数据池中 |
| `NodeEdgeDecomposer` | 对象 → 行集合（1 实体行 + N 属性行） | 反射 + InvariantCulture 序列化 |
| `ObjectAssembler` | 行集合 → 对象（TypeId 反查属性名，反射赋值） | Advisor 说"这就是计算"——对，但实测它便宜得惊人 |
| `UniversalEntityRepository` | 磁盘表仓储：逐行 / Batch / SoftDelete / BulkCopy / 子图预取 / OPENJSON 批量 | 全参数化，零 SQL 拼接 |
| `MemoryOptimizedEntityRepository` | 内存优化表仓储：TVP 单次往返写入 | BulkCopy 不支持内存表，TVP 是唯一正解 |
| `EngineRouter` | Role=4 指令 → 路由目标 | 内存路由，无加密协议 |

### 2.3 创世与自愈

```text
清空全表 → 引擎启动 → 发现 Role=1 行数为 0 → 自动播种 6 行创世数据
（1 类型 + 4 属性定义 + 1 路由指令）→ 内存元数据就绪 → 万物可生长
```

新增一种业务类型 = 往池子里插几行数据。**零 DDL、零编译、零部署。**

## 三、六轮演进实录（全部实测）

### 第 1 轮：原型骨架
单表模型 + 拆解/组装/路由引擎 + 11 个内存测试。验证"对象 ↔ 行集合"往返成立。

### 第 2 轮：真实库落表（起点：492 entities/s）
建库 `GenesisIso`、建表、真实 SQL 读写集成测试。逐行 `ExecuteNonQuery` 写入 5 万行 = **15.4 秒**。此刻瓶颈 100% 是 I/O 往返（60001 次）。

### 第 3 轮：往返同化（7.0 倍 → 3955/s）
- 写入同化：全部行压成 `DataTable`，`SqlBulkCopy` **1 次往返** → 1.86s
- 读取同化：一条子图预取 SQL 拉回实体行+全部属性行 → 0.66s
- **60001 次往返 → 2 次。**"往返也是一种实体，图的整体搬运才是读写。"

### 第 4 轮：引擎自举（Bootstrap）
元数据真实落库；`MetaCache.LoadAsync` 改为从池中加载；空池自播种。21/21 测试。
**质变：清空全表，引擎也能自愈创世。改元数据 = 改几行数据。**

### 第 5 轮：物理换装 In-Memory OLTP（1.7 倍 → 6858/s）
内存优化表 + TVP 存储过程：写入 0.81s、读取 0.61s。实测踩掉四条硬约束（见 §5.2）。

### 第 6 轮：去数据库化（8.6 倍 → 72992/s）
进程内 KV 引擎 + 手工二进制打包：
- `ConcurrentDictionary`：写入 **36ms**（138.9 万行/s）、读回 **23ms**（217.4 万行/s）
- `FASTER KV`（嵌入式可持久化 LSM）：写入 81ms、读回 38ms

### 五引擎光谱（同规模：10K 实体 = 5 万行）

| 引擎 | 写入 | 读取 | 总计 | 吞吐 | IPC 往返 |
|---|---|---|---|---|---|
| ① 逐行 + 磁盘表 | 15419 ms | 4810 ms | 20311 ms | 492/s | 60001 |
| ② BulkCopy + 磁盘表 | 1858 ms | 655 ms | 2528 ms | 3955/s | 2 |
| ③ TVP + 内存优化表 | 809 ms | 611 ms | 1458 ms | 6858/s | 2 |
| ④ 进程内 ConcurrentDictionary | **36 ms** | **23 ms** | **137 ms** | **72992/s** | **0** |
| ⑤ 进程内 FASTER KV（可持久化） | 81 ms | 38 ms | 176 ms | 56818/s | **0** |

**累计提速 148 倍。每实体全链路 13.7 微秒（含拆解+写入+读回+组装）。**

## 四、哲学 vs 实测：对账表

这是白皮书最重要的部分——哪些哲学被数据证实，哪些被证伪。

### 4.1 被证实的

| 哲学宣称 | 实测证据 |
|---|---|
| "结构同构消灭 JOIN" | 子图预取 1 条 SQL；进程内路径连查询都消失，纯指针分组 |
| "组装近乎零成本" | 5 万行内存组装 30–55ms，占全链路 <3%（进程内路径下占 ~35%，见下文） |
| "引擎同化可行" | Role=1/4 落库 + 自举，清池自愈，21 测试覆盖 |
| "数据库可以是哑的" | 六个引擎存同一种行结构，上层组件零改动 |
| "I/O 是真正瓶颈" | 148 倍提升全部来自消灭往返与持久化开销，计算成本几乎没变 |

### 4.2 被修正的

| 早期宣称 | 实测修正 |
|---|---|
| "零计算" | 计算从未消失：拆解/组装就是遍历+反射+编码。修正为"**计算便宜到可以忽略，I/O 才是价格**"。进程内路径下组装反而占 35%，成为新瓶颈——这恰恰证明 I/O 税已被清零 |
| "一张表构建所有业务"（安全角度） | 参数化查询本来就能防注入；同构混淆"让黑客看不懂"的价值**依赖加密层，本轮未实现**，不能作为已得安全收益 |
| "单表亿级无压力" | 未验证。5 万行≈6MB 数据 → 1 亿行≈12GB 裸数据，进程内对象开销 ×3–5 ≈ **40–60GB 内存**，单机接近极限。规模天花板是真实存在的问题（§6） |

### 4.3 外部预测 vs 实测（预测必须实测的教训）

| 预测（E5 级） | 实测（E2 级） | 偏差 |
|---|---|---|
| BulkCopy 后写入"绝对 200ms 以内" | 1945 ms | **10 倍** |
| "吞吐迎来百倍爆发" | 累计 6.9 倍（当时） | 差 14 倍 |
| 内存表写入"暴跌到 30ms" | 793 ms | **26 倍** |
| 内存表读取"快十倍" | 快 22% | **4.5 倍** |
| "Redis 十几毫秒" | 未测（本机无 Redis）；进程内字典 36ms 已构成更近路径的上限 | 不可比 |

**教训：架构直觉只能指方向，数字必须自己跑出来。**

## 五、实证的工程法则（可直接复用的结论）

### 5.1 往返定律
在消灭全部计算之前，先消灭往返。**N+1 往返是万恶之首**：60001 次 → 2 次 = 7 倍；2 次 → 0 次 = 再 8.6 倍。任何"每行一次查询"的写法都在物理上封死了性能上限。

### 5.2 SQL Server 硬约束实录（每条都有报错号）
1. UTF-8 无 BOM 文件 + 中文注释 + sqlcmd（GBK 解码）= 静默吞列（B1，最阴险）
2. `SqlBulkCopy` **不支持**内存优化表 → TVP + PROC 是唯一批量正道
3. 内存优化表：不支持 `TRUNCATE`；索引必须内联定义（10794）；索引不支持 `INCLUDE`（10664）；DROP TYPE 前必须先 DROP 引用它的 PROC（3732）
4. `MemorySizeBits` 是 2 的幂字节数：2^20=1MB 装不下 6MB 数据 = 刷盘风暴卡死（B10，数量级教训）

### 5.3 自举定律
元数据落库 + 空池自播种，使"改结构"从 DDL+发布 变成 INSERT 几行。**接口不变、数据源同化**——这是低成本高收益的一步。

## 六、代价、边界与风险（不想清楚就不该继续）

1. **ACID 交换速度**：进程内引擎绕过事务/恢复/审计体系。④ 重启全丢；⑤ 靠 checkpoint，崩溃恢复未验证。SQL Server 路线（③）仍是唯一完整 ACID 选项。**五引擎是光谱，不是替代链。**
2. **内存天花板**：进程内全驻留路线在 ~千万行级（含对象开销）触碰单机内存墙；GC 压力未测。
3. **未竟的验证**：FASTER 崩溃恢复；100K/1M 行曲线；并发会话与乐观冲突；跨实体 Edge；雪花 ID；加密层。
4. **安全的真话**：同构 + 参数化 = 防注入成立；"黑客看不懂数据"需要引擎层加密，未做；防枚举需要非顺序主键（Guid 已占位，雪花 ID 未做）。

## 七、三条未竟之路（下一步的决策面板）

| 路线 | 内容 | 已知收益 | 已知代价 | 前置条件 |
|---|---|---|---|---|
| A. 接入落地 | `IUniversalStore` 抽象 + 五引擎可插拔 + 按 Role=4 指令动态选择引擎 | 六轮成果从测试代码变成正式架构；上层 BLL 与物理引擎解耦 | 一次性重构工作量；测试项目→DAL 迁移 | 无 |
| B. 规模探底 | 100K/1M 行曲线：字典 GC 压力、FASTER 页置换、内存表哈希桶衰减 | 拿到各引擎真实天花板，回答"亿级是否可行" | 纯验证，不产出架构 | 无 |
| C. 终极形态 | 热内存 + DirtyGraph 异步落盘 + LRU 冷加载（Event Sourcing） | 前端零往返 + 可持久化的统一体 | 并发一致性、崩溃恢复语义全新设计 | 建议 A 先行 |

**架构师意见**：A → B → C。A 是把已验证的东西固化（低风险高确定性）；B 的数据在 A 完成后更有意义（压测对象应是正式接口而非测试代码）；C 是哲学终点，但它的正确性设计（一致性、恢复）比速度更难，值得在 A、B 之后单独开篇。

## 八、结语

六轮下来，从 15.4 秒到 0.137 秒，这条曲线背后其实只有三句话：

1. **往返同化**（60001 → 2 → 0）贡献了绝大部分加速；
2. **存储同化**（磁盘 B+树 → 内存表 → 进程内）贡献了剩余全部；
3. **计算从未是敌人**——同构消除了转换，剩下的每微秒都是干正事的。

"一生二，二生三，三生万物"在工程上的对应物是：**一种行结构（一）、读写与角色二分（二）、元数据与引擎规则（三）、任何业务（万物）**。哲学没有打折地落了地——落地的方式不是靠相信，而是靠 24 个测试和 6 张基准表。

> 剩下的路只有一条原则：**每一句"理论上更快"，都必须变成表格里的一行实测数字。**
